  • 選用 TTL-based lock 而非外部 lock 服務 — 降低維運複雜度
  • 路由策略可切換(非寫死)— 新流程類型不必動核心
  • 流程事件 → Kafka — SRE / analytics 自助追蹤
  • 事故處理從救火改為流程驅動

Zenbo 跨裝置 VoIP SDK(ASUS 智慧機器人)

ASUS Zenbo 機器人需要與 iOS 裝置即時音視訊通話,但機器人 runtime 不是標準 iOS 環境 — 信令、NAT 穿透、通話生命週期都得自行設計;同時其他產品團隊不應該被迫去懂 WebRTC 才能用通話功能。決策: 把整個通話協商、NAT 穿透、狀態機 包成單一進入點的 SDK,而非暴露 raw WebRTC 元件 — 讓其他團隊不用碰 ICE candidate 或 SDP 細節即可嵌入視訊通話。機器人端硬體整合與 iOS 端 共用同一份 call state model,而非各自維護一份 — 這在問題發生前就消滅了一整類跨裝置 race condition,因為沒有第二個狀態機可以漂移。結果: 其他產品團隊只需呼叫少量 SDK API 即可嵌入 Zenbo↔iOS 視訊通話;此 SDK 成為 ASUS 智慧機器人通話能力的底層。

  • Reviewer 不用每次都問「你有想過 X 嗎」 — 模板已經強制檢查 X。
  • 資深判斷不再卡在某個人的腦袋裡,而是 repo 內可被審計的 Skill 與 prompt。
  • 新進同事 ramp-up 更快,因為團隊的 review 判斷標準是明確、可重用的。
